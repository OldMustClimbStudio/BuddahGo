# FishyFacepunch tolerates a missing Steam client

A Solo Match must run with Steam closed. Today `FishyFacepunch.Initialize` calls `SteamClient.Init` with no guard (`FishyFacepunch.cs:98-101`), and the call throws `NoSteamClient` when Steam is not running. The `SteamNetworking.AllowP2PPacketRelay` call that follows it (`:103`) also needs a running Steam client. The exception happens during the TransportManager step of `NetworkManager.InitializeComponents`, so the client, server, scene, observer and prediction managers are never initialized (N3 in `Docs/optimization/p0-validation.md`). `Multipass.Initialize` initializes every child transport, so selecting Yak for solo does not avoid the call.

We patch the plugin's initialization to tolerate the failure. Online entry points then report that Steam is unavailable, while the Solo Match runs on Yak through the same NetworkManager. We chose this over a second NetworkManager setup for solo. The only NetworkManager lives in `MainMenu.unity`, and duplicating it would split its transport, observer and prediction settings into two copies that have to be kept in sync. Steam is checked only at startup, so if Steam is launched after the game, the player has to restart the game before online play is available. FishyFacepunch now has its own assembly definition, so the change stays inside that assembly. It is a local change to third-party code and must be kept when the plugin is upgraded.
