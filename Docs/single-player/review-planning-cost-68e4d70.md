# 五 AI 规划成本 review 与算法重构思路

2026-10-02；基于 `68e4d70`（`feat/single-player-mode` / PR #59）。只读分析，未运行新的 Player 测量。
排名与结算的进行中改动不在本文范围内。

## 结论

1. 93 ms/帧 不是"五个 AI 太多"，也不是缓存不够。重规划频率是控制粒度的 3 倍、全部在主线程、后端是 Mono，三者叠加。沿"逐位等价 + 缓存"的路线最多再拿 20–30%，达不到需要的 10×。
2. 更根本的问题是算法与车辆动力学不匹配。这辆车线性阻力为 0，没有刹车，只有推力方向可控，本质是一艘推力矢量飞船。车头朝向是一个受限扭矩的双积分系统，转 90° 需要 1.3–1.5 秒。beam search 用 3 个键 × 20 个 0.15 秒块（3^19 条序列）去逼近的，其实是一个一维量：目标朝向。
3. 因此"更优解"不是把 beam search 做快，而是换成**推力矢量引导 + 时间最优姿态控制**：每 tick O(1)，精度高于 beam（60 Hz 决策 vs 150 ms 块、连续目标朝向 vs 3° 分辨率），五个 AI 的规划成本降到微秒级，性能问题整体消失。beam search 保留为对照和可选的避让层。
4. 入弯转圈修复导致的圈速退步，很可能是 ±180° 硬墙把"车尾朝前全推力刹车"这个最大减速姿态一起砍掉了。第四节给出验证方法和临时缓解。

实现者应当：先按第五节验证硬墙假设（半天），然后直接做第六节的新控制器（第一版两三天可出离线圈速），不要再在 beam search 上做缓存级优化。第三节的性能手段只在决定保留 beam search 时才需要。

## 一、工作量推导（Normal V5，TickRate 60）

| 项 | 推导 | 每次 Plan |
|---|---|---:|
| tickDelta | 1/60 | 16.67 ms |
| 控制块 `block` | round(0.15 / 0.01667) | 9 tick |
| 深度 `depth` | ceil(3 / (9 × 0.01667)) | 20 层 |
| 每首键 beam 宽 `width` | 48 / 3 | 16 |
| 候选展开 | 3 × (1 + 19 × 16 × 3) | 2,739 |
| 模型 `Step` | 2,739 × 9 | 24,651 |
| 投影线段检查 | 2,739 × (2 × 12 + 1) | 68,475 |
| DiverseSearch 比较 | ≤ 2,739 × 16 | ≈ 44,000 |

每 3 tick 重规划，5 个 AI，60 Hz → 每秒 100 次 Plan。按 compare-final 实测 9.56–17.82 ms/次，每秒需要 1.0–1.8 秒 CPU。这与 compare-final 的 291 ticks / 8.965 s（≈ 32 ticks/s）吻合：系统处在 tick 积压平衡点，帧时由积压决定。

单次展开实测 3.5–6.5 µs，对 9 步 Euler + 25 次点积 + 16 次比较而言偏慢，差距主要是 Mono 不内联 `Vector3` 运算符，以及 `Candidate`（约 56 字节）在插入/去重时的多次拷贝。

已核实的有利条件：`BuddahPredictedMotor.BuildReplicateData` 对无主对象每 tick 只调一次 `TryGetOverride`（990 次 / 165 tick = 6 车），没有 reconcile 重放放大；AI 输入只在服务器产生。

## 二、车辆动力学（算法选择的依据）

来自 `Buddah.prefab` 与 `BuddahPredictedMotorConfig`：

| 参数 | 值 | 含义 |
|---|---:|---|
| 质量 | 2 | |
| 推力 | 50 → a = 25 m/s² | 恒定全油门，沿车头方向 |
| 线性阻力 | 0 | 速度方向不会自动跟随车头 |
| 速度上限 | 80 m/s | 模型按 `ClampMagnitude` 处理 |
| 地面摩擦减速 | ≈ 1.96 m/s² | 唯一的"自然"减速，很弱 |
| 扭矩 | 30（× TurnInputMultiplier） | 车头角加速度 ≈ 2.4–4.8 rad/s² |
| 角阻力 | 0.05 | 可忽略 |
| 空挡角速度衰减 | 3 rad/s² | 松开转向时的"偏航刹车" |
| maxAngularVelocity | 未设置，Unity 默认 7 rad/s | 不构成约束（峰值约 2–2.4 rad/s） |

推论：

- 横向加速度 = 25 · sin θ，θ 是车头与速度方向的夹角。80 m/s 时最小转弯半径 256 m（θ = 90°），50 m/s 时 100 m。`PreparePace` 的 `sqrt(a · factor / κ)` 就是这个极限，公式本身正确。
- 要在弯中保持 50 m/s 过 100 m 半径，车头必须与速度方向垂直；要减速，θ 必须大于 90°；最大减速是 θ = 180°，车尾朝前。**偏航"刮速"是这辆车唯一的转弯和刹车手段，不是缺陷。**
- 车头是双积分系统：全扭矩加速、空挡以 3 rad/s² 衰减。从静止转 90° 并停住约 1.3–1.5 秒，行驶距离 100 m 以上。一个 0.15 秒控制块只改变车头 1.5–3°。
- 因此在 3 秒时域内，可执行的动作本质上是"加速偏航 → 保持 → 衰减"的 bang-bang 曲线，自由度是目标朝向（和到达时刻），不是 3^19 条键序列。beam search 的绝大多数展开在枚举同一条曲线的离散变体，DiverseSearch 的存在本身就是这个冗余的证据。

## 三、若保留 beam search：性能手段的顺序

只在决定不换算法时才做。顺序按杠杆大小。

1. **IL2CPP 对照**（零代码）。`ProjectSettings.asset` 的 `scriptingBackend` 为空即 Mono。重建后跑同条件窗口，预期单次 Plan 2–4×。
2. **重规划周期与控制块对齐**。A：`ReplanTicks` 3 → 9，÷3，反应时间 50 → 150 ms。B：首块长度 = `ReplanTicks`，后续块 9 tick，假设与执行一致，成本 +5%，反应时间不变。先测 A，退步则改 B。
3. **Plan 移到工作线程，T+1 应用**。`Plan` 是纯函数（`BuddahLocomotionStep.Compute` 纯函数；`Mathf`/`Vector3` 线程安全）；有状态部分只有每实例私有的 `_nearSegment`/`LastObservation` 和主线程先调一次的 `PreparePace`。现有 `ReactionTicks` + `_pendingSteering/_applyTick` 机制正好是"延迟 1 tick 应用"的语义。派发前把 profile 字段拷贝成 struct，工作线程不碰 `Rigidbody`/UnityEngine.Object 原生属性。主线程成本降到只剩读状态。
4. **不改决策的微优化**：`Geometry` 预计算每段 tangent yaw；DiverseSearch 条件重排为 position → velocity → yawRate → DeltaAngle；`searchSegments` 12 → 8（单块最大位移 86 × 0.15 ≈ 12.9 m ≈ 6.5 段）。合计 20–30%。
5. 远期粗步长、Burst：留到以上数字出来再决定。

不要做：继续以 `Legacy*` 逐位等价为验收门；先做 Burst；把错开规划 tick 当主要手段（只平滑 P95，不降总量）；在摆头没消除前缩 `BeamWidth`。

## 四、圈速退步（118.1 → 126.0 s）的假设与验证

**假设**：分支约束 `|HeadingError| > 180° → 淘汰` 是硬墙，而最大减速姿态恰好在 θ = 180°。需要重刹入弯时，最优候选贴着墙走，数值上略过 180° 就被整条淘汰，planner 只能用 θ < 180° 的不充分减速，于是更早减速或走更宽的线，圈速退步。文档记录的 40/7555 次 neutral 回退也与"墙边候选全部被砍"一致。

**验证**（只观察，半天）：

1. `PlanObservation` 增加最优候选在各块的 `HeadingError` 最大绝对值，以及 `rejectedWinding` 在刹车段（`forwardSpeed > pace`）的占比。
2. 用现有 harness 跑一圈，看 `rejectedWinding` 是否集中在刹车段，最优候选的 `HeadingError` 是否频繁落在 150–180°。
3. 成立则改为软约束：允许到 ±270°，超过 180° 的部分加二次惩罚 `WindingWeight × (|e| − 180)²`。整圈（360°）仍然昂贵，但车尾朝前刹车可用。

这一步是 beam search 路线的止血，不是终点。第六节的新控制器不存在这个问题，因为它直接把目标朝向算出来，θ = 180° 是一个合法的解而不是边界。

## 五、我前一版判断的更正

前一版 review 把"偏航刮速"判断为目标函数缺陷，建议加 yaw 与速度方向夹角的惩罚。读到线性阻力为 0 后，这个判断不成立：刮速是物理必需。`SpeedWeight` 对超速的对称惩罚本身没错，它只是在告诉 planner "需要减速"，而 planner 用唯一可用的手段执行。真正的问题是执行这个意图的搜索方式太贵、分辨率太粗，以及第四节的硬墙。

## 六、更优算法：推力矢量引导 + 时间最优姿态控制

> **2026-10-02 起，本节的逐次修正已被 [thrust-vector-controller-spec.md](thrust-vector-controller-spec.md) 取代。** 本节保留为推导与修正记录；实现、校准、验收以规格文档为准。规格之外的规则改动先写进规格再实现。

### 结构

```
每 tick（服务器，每个 AI）：
  1. 投影到赛车线（沿用 SplineRacingLine.Project，带 nearSegment 提示，±3 段即可）
  2. 引导层：算出当前想要的加速度向量 a_des
  3. 把 a_des 转成目标朝向 ψ_des（推力只能沿车头）
  4. 姿态层：bang-bang 选键 {-1, 0, +1}，把车头时间最优地转到 ψ_des
```

### 引导层（guidance）

**2026-10-02 修正**：第一版写的 `ψ_des = atan2(a_des)` 是错的。推力大小恒为 25 m/s²，可控的只有方向；a_des 很小时车头会沿切线，结果是全推力加速而非轻微修正，直道上 a_des ≈ 0 时方向无定义。实现者离线 236 组参数无一完成整圈，原因在此。以下为修正后的映射，在**速度方向**的坐标系中做，分两个独立决定。

输入：投影点、切线 t、曲率 κ、pace 曲线 v_ref(s)、横向误差 e、横向速度 ė、速度 v 及其方向角 ψ_v。

**(1) 横向分量决定夹角大小。**
a_lat = v² κ − k_p · e − k_d · ė（在速度方向的法向上，带符号），限幅 |a_lat| ≤ 25。推力横向分量 = 25 · sin θ，θ 为车头与速度方向的夹角，所以 sin θ = a_lat / 25。两个候选解横向分量相同、纵向分量一正一负：
- 加速解：|θ| = asin(|a_lat| / 25)
- 减速解：|θ| = π − asin(|a_lat| / 25)

**(2) 速度误差决定取哪个解。**
这辆车不能匀速：θ < 90° 必加速，θ > 90° 必减速（地面摩擦 1.96 m/s² 可忽略）。用迟滞带：v < v_ref(s + L) − margin 取加速解，v > v_ref(s + L) + margin 取减速解，带内保持上一次选择。它会以车头响应时间的量级在两解间慢速切换，这是这辆车唯一的"匀速"方式，也是 beam search 之前摆头的物理来源。v 到达 80 上限时取加速解，钳制吃掉多余纵向分量。L = v · τ，τ ≈ 0.8–1.2 s。

**(3) 保护与优先级（第二次修正，2026-10-02）。**
实现者离线发现：横向需求饱和到 25 时两解都退化为 90°，纵向制动归零，而饱和恰恰发生在最需要刹车的超速入弯时（实测 76.56 m/s 对目标 41.11 m/s）。所以两个分支的优先级不同：
- **减速分支纵向优先**：θ = clamp(π − asin(|a_lat|/25), 120°, 150°)。纵向制动保证 12.5–21.7 m/s²，与 pace 回传假设的 12.5 一致；横向只拿 sin θ 给的 12.5–21.7 m/s²，剩余横向误差由 PD 项在后续 tick 收回。150° 上限同时避开 ±180° 的最短角歧义（绕圈来源）。
- **加速分支横向优先**：θ = asin(min(|a_lat|, 25)/25)。饱和时 90° 不加速，是正确行为。
- 触及 80 上限只在 v_ref(s + L) 也接近 80 时才强制加速解；超速入弯时按迟滞带正常取减速解。
- a_lat 中的 v²κ 用**当前位置**的曲率；选解用**前瞻点**的 v_ref。两个前瞻用途不同，前瞻曲率乘当前高速会在直道末端必然饱和。
- θ 的符号跟随 a_lat 的符号，并在同一分支内保持稳定，不每 tick 重算。
- v 很小时（起步、碰撞后）速度方向无意义，用切线 t 代替 ψ_v。

ψ_des = ψ_v + θ。

**选解参考速度（第四次修正，2026-10-02）。** 去掉整圈旋转后离线 DNF（横向误差 > 200 m），定位到 2.917 s：v = 52.91，pace(s) = 48.25，pace(s + L) = 60.14，前瞻看到出口就放开刹车，车还在弯内。pace 曲线已向后回传，pace(s) 本身就是"现在允许的最高速度"，前瞻只能用来提前刹车，不能用来提前放开。选解参考速度改为 **min(pace 在 [s, s + L] 窗口内的所有采样)**，不只是两点 min，否则漏掉窗口中间更紧的弯。每 2 m 一个采样，L ≈ 50–80 m 即 25–40 次比较。迟滞带不变。

注：之前的 120.883 s 完成圈带有整圈旋转，旋转本身就是刹车；去掉旋转后 DNF 说明刹车逻辑此时才第一次真正受考验。beam 在纯模型中同样 DNF（86.6 s），离线整圈没有墙，比真机严格；离线通过才有意义，真机的墙会掩盖控制器缺陷。

**首圈结果与摆动修正（第五次，2026-10-02）。** 第四次修正后离线整圈 198.083 s、真实单圈 165.633 s，展开朝向在 ±180° 内，整圈旋转解决。但换侧 52/68 次、真实 75 次侧接触、离线最大横向误差 125.6 m。每次换侧车头摆 100° 以上、约 1 s，68 次 ≈ 60 s，就是与 ~105 s 的差距。扭矩 modifier 只缩短每次摆动 20%，去掉摆动是 10 倍收益，所以顺序是：先诊断、再修摆动、再扭矩、再三圈。

诊断（PlanObservation CSV）：减速分支时间占比；减速分支内 θ 直方图；每次换侧时的 |a_lat| 与分支。

两条修正：
- **去掉 150° 上限**。它是为 `DeltaAngle` 最短弧歧义加的，第三次修正的连续分支 φ 已消除歧义。残留副作用：a_lat 小时减速解卡在 150°，一边刹一边被 12.5 m/s² 横推，横向误差长出来，PD 换侧，再被反向横推。改为 θ = max(120°, π − asin(min(|a_lat|, 25)/25))，取 178° 作防奇异上限；a_lat 小时自然接近纯刹车。120° 下限只在饱和时生效。
- **pace 因子 0.8 → 0.9–0.95，并加"保持"模式**。这辆车弯内的自然平衡是 θ = 90°、v = sqrt(25/κ)：纯横向、纵向零、速度不变。因子 0.8 把 pace 压到 80%，弯内横向需求只有 20，加速解 53° 与减速解 127° 相隔 74°，车在两者间每秒切换一次。因子提高后两解靠拢；迟滞带内且 |a_lat| 需求 ≥ 约 18 时取 θ = 90°，不加速不减速。这是这辆车唯一的匀速姿态。

离线 198 s 慢于真机 165 s 说明没有墙时车跑得更野，墙在替控制器纠偏。摆动修掉后两数应靠拢且离线更快。

诊断结果（9,916 行）：减速占 71.95%；减速时间内 θ 顶在 150° 上限 37.07%、120–125° 44.68%，两头合计 82%；68 次换侧中 43 次在减速，换侧时 |a_lat| 中位数 3.19 m/s²。判断成立。

**e_target 跳变（第六次修正，2026-10-02）。** 第五次修正后仍有两组绕圈。定位到 7.267 s：e_target 从 −179.986° 翻到 +179.912°，φ 从 −0.653° 跳到 +359.245°，车没动而输入反向，随后重锚再反转。原因是第三次修正把 e_target wrap 到 ±180°，而 e_target = e_v + θ 可达 ±208°。规则改为：
- e_target 不 wrap：e_target = e_v + θ 直接相加（e_v 为速度方向相对切线的 wrap 值，θ 带符号），clamp 到 ±178°。连续；换侧时从 +150° 到 −150°，φ = −300°，控制器自然经切线方向摆过去，"换侧经过切线"由此自动成立。
- 不再因 |e_car| > 180° 单独重锚。控制产生的越界只是数值毛刺，e_car 与 e_target 同步平移 360°，φ 不变。
- 外部碰撞恢复：|e_car| > 200°，或近期碰撞标记且 |e_car| > 180°，才取最短弧重锚。控制器自身到不了 200°。"旋转 300° 后顺转 60°" fixture 仍成立。
- |e_v| > 90°（车倒退）视为恢复状态，e_target = 0 对准切线，不走正常分支。

**第六次修正后的结果与横向跟踪疑点（2026-10-02）。** 跳变消除（7.267 s φ 保持 1.333°、输入保持 0）。但离线仍 DNF：53.767 s、最大横向误差 200.285 m，120° 下限占减速时间 51.72% / 52.76%；诊断组另见 27.954 m 投影跳变。

判断：减速分支在 120° 时横向推力 21.7 m/s²，足以让任何横向误差收敛，误差却长到 200 m。推力够大而误差发散，只有两种解释：推的方向错，或 PD 增益振荡。真机 165 s 靠墙挡住，离线无墙暴露。因此 **0.5→0.4 的条件暂不满足**：a_lat 饱和有 v²κ、k_p·e、k_d·ė 三个来源，直方图分不出是谁。

顺序：
1. 分解所有顶在 120° 的 tick 的 a_lat 为 v²κ、k_p·e、k_d·ė 三项及占比。v²κ 占大头才是刹车晚，再做 0.5→0.4；PD 占大头是跟踪问题，走 2、3。
2. 直线偏移 fixture：直线赛车线，车在线右侧 10 m、50 m/s 沿线方向，跑 4 s。断言首 tick θ 朝向线、e 单调减小、不过线超过 2 m。`FinalSteeringSign` ±1 各一次。`Project` 的 lateral（`Cross(up, tangent)`）、a_lat 法向、θ 符号、motor 转向符号四处约定只要一处反了就是现在的现象。
3. 增益量级：横向动力学是带约 1 s 执行滞后的双积分，k_p 0.1–0.3、k_d 0.5–1.0，k_d ≈ 2·sqrt(k_p) 临界阻尼（如 0.16 / 0.8）。k_p ≥ 1 全在振荡区；k_d·ė 单独可饱和（摆头时 ė 可达 20 m/s）。

27.954 m 投影跳变是症状：横向误差超过十几米后小窗口投影在平行/交叉路段选错段。记录，不修，跟踪修好后应消失。

**大方向盘点（2026-10-02，第六次修正后）。**

方向成立：六次修正没有一次推翻"推力恒定、只控方向、无刹车"框架；α/β 实测与推导一致；整圈旋转靠纯几何规则消失而非调参；刹车姿态 fixture 全过。

仿真与真机一致：离线 198 s / 125 m / 52 次换侧，真机 165 s / 26 m / 68 次换侧 / 75 次接触。真机的墙把离线的 125 m 出线截成 26 m，每次截一次接触；真机更快是墙在免费纠偏。模型没有骗人，离线修好的会直接转移。但 beam 离线同样 DNF 而真机 118 s，所以"离线无墙整圈"比 beam 通过过的任何测试都严；保留，但公平差距是真机 165 对 118。

设计缺口（review 作者侧）：姿态层用了时间最优开关曲线，引导层的横向修正却只有朴素 PD。横向是双积分，执行器是要摆约 1 s 的车头，推力还会饱和。带滞后、会饱和的双积分用 PD，表现就是：误差变大 → PD 饱和 → θ 钉在 120° → 21.7 m/s² 推回 → 过线 → 反向饱和，振幅随滞后增长。52% 顶下限、换侧时 |a_lat| 中位数 3.19、误差 200 m 是同一机制的指纹。

**第七条（结构性，预计最后一条）**：横向修正也预测执行滞后。e_pred = e + ė·T + ½·a_now·T²，T 为车头从当前 θ 摆到目标 θ 的时间（按 α 算，0.3–1 s），修正量 = −k·e_pred，k 0.1–0.2。误差长出来之前就反向，不等饱和。符号检查与低增益仍要做，但即使两者正确，朴素 PD 在此系统上也只是勉强稳定。

决策点：符号、低增益、预测横向三条做完离线仍不能整圈，则纯反馈横向不够，改混合：速度/刹车用推力矢量（已验证），横向用 3–5 个 θ 偏移的短闭环 rollout 选一（约 beam 成本 3%）。可选层此时变必选。三条很便宜，先做完再说。

**下一项（上述分解确认 v²κ 占大头后再做）**：120° 下限占减速时间 44.68%，即刹车区近半时间横向需求饱和、车已对弯道超速。`PreparePace` 回传按 `2f * acceleration * .5f` 即 12.5 m/s² 规划，控制器在 120° 时恰好给 12.5，零余量；车头摆到 120° 要约 1 s，这 1 s 就落后曲线。把 0.5 降到 0.4（按 10 m/s² 规划刹车），给摆动时间留余量。

与 `PreparePace` 的关系：pace 曲线的回传刹车假设 12.5 m/s² 减速，对应减速解 θ ≈ 120°，一致，不需要新的速度曲线。

### 姿态层（attitude）

车头误差 φ = DeltaAngle(ψ, ψ_des)，角速度 ω，全扭矩角加速度 α（2.4 或 4.8，按实际 multiplier 读 `BuddahPredictedMotorConfig`），空挡衰减 β = 3。

双积分时间最优控制的开关曲线：从当前 (φ, ω) 出发，若现在松开转向，到角速度衰减为零时还会转过 ω·|ω| / (2β)。

```
remaining = φ − ω·|ω| / (2β)      // 松开后仍剩的误差
if |remaining| < deadband:  key = 0
else:                        key = sign(remaining)
```

deadband 取 1–2°，加一点迟滞避免抖动。这就是整个"规划"。每 tick 执行，分辨率 16.7 ms，而 beam 是 150 ms。

**φ 的定义（第三次修正，2026-10-02）。** 离线首圈 120.883 s 可完成，但展开朝向到 −344°～+1989°：减速角换侧时（+130° → −130°）`DeltaAngle` 选了经过车尾的 100° 最短弧，每次换侧都同向累积。φ 改为连续路线朝向分支上的误差，与 `ForwardSimPlanner.AdvanceHeadingError` 同一思想：

- e_car：车头相对切线的误差，连续累积。每 tick 加真实 yaw 增量，减切线转角，不 wrap。
- e_target：ψ_des 相对切线的误差，wrap 到 ±180°。控制器从不命令超过 ±150°，天然在分支内。
- φ = e_target − e_car，不 wrap。remaining 开关曲线不变。换侧时车头从切线方向（车头侧）摆回。
- **重锚**：|e_car| > 180° 时重置为 wrap 后的最短值。控制器自身不会越过 150°，超过 180° 只能来自碰撞等外部扰动，此时顺着最短分支回正，而不是反向转一整圈。等价于 beam 的"起点取最短分支"。
- 换侧死区：|a_lat| < 约 3 m/s² 时沿用上一侧的 θ 符号。每次换侧是一次大摆头，S 弯和 PD 过冲造成的频繁换侧要压掉。

### 为什么它更优

- 精度：目标朝向连续，决策 60 Hz。beam 的首键每 150 ms 只能是三选一，车头分辨率 1.5–3°，摆头来自这个粗粒度与有限时域的组合。
- 圈速：弯道用的就是物理极限（a_normal = v²κ 直接要求 θ 满足 25 sin θ = v²κ），不多不少；刹车段 θ 自然超过 90°，需要时到 180°，没有硬墙。
- 成本：每 tick 一次投影（7 段）+ 几十个浮点运算。五个 AI 合计 < 0.05 ms/帧，第三节全部不再需要。
- 可调性：难度 = τ、pace factor、deadband、反应延迟、给 ψ_des 加噪声。比 beam 的 9 个权重直观，容易校准 Easy/Hard。

### 可选第三层：短闭环 rollout（避让与路线选择）

需要超车/避让时，不要回到键序列搜索。候选 = 5–7 个横向偏移（`LateralOffset` 的离散值），每个候选用上述控制器做 1.5–2 秒的闭环 rollout（90–120 个模型步），按进度/接触/横向误差打分选一个，每 0.5 秒重选一次。总成本 ≈ 700 步/次，是现在 24,651 步的 3%，而且 rollout 是闭环的，比开环键序列更有意义。这是性能与精度真正可调的旋钮。

### 实现落点

- 新建 `ThrustVectorPlanner : ISteeringPlanner`，与 `ForwardSimPlanner` 并存；`AIDifficultyProfile` 加一个选择开关，`AIRacerDriver` 按开关实例化。现有接口 `Plan(state, parameters, line, profile, tickDelta, previousKey)` 已经够用，`ReplanTicks` 设为 1。
- `SplineRacingLine` 增加每段曲率（`PreparePace` 里已经算了，存下来即可）和 `Project` 的小窗口版本。
- `PlanObservation` 填 ψ_des、a_des、φ、ω、key，harness 的 plans CSV 直接可用。
- 模型层 `BuddahMotionModel` 不变，继续用于离线验证和可选 rollout。

### 验证顺序

1. **离线**（EditMode，不需要 Player）：用 `BuddahMotionModel` + `spin-entry.json` 的赛车线做纯模型整圈，比较新控制器与 `ForwardSimPlanner` 的模型圈速、横向 RMS、最大 |e|。半天可出结果，用来调 τ、k_p、k_d、deadband。
2. **harness 单圈**：`--ai-a1-output` 跑真实 Player 一圈，对照 118.1 s / 20 接触。
3. **harness 三圈**：`--ai-a2-output`，对照 116.5 s（A2）与 126.0 s（spin-fix）。
4. **五 AI 性能窗口**：同 compare-final 条件，预期中位帧时 ≤ 20 ms、net ticks ≈ 540/9 s。
5. **模型误差窗口**：沿用 ai-spin-fix.md 的无接触窗口检查，新控制器不改模型，通过率应不低于 293/297。

### 为什么成本能差三个量级

不是控制器更聪明，而是它不搜索。beam search 不知道答案的形状，所以枚举几千条键序列。这辆车有两个结构让答案有闭式解：推力只沿车头，所以"想要的加速度"与"车头该朝哪"一一对应，一个 `atan2` 算出；车头是受限扭矩的双积分系统，时间最优控制是经典的开关曲线，一个不等式判断。beam search 用 24,651 步积分近似的，就是这两个公式的输出。

### Drawback（与 beam search 相比）

1. **没有前瞻，只有反馈加前馈。** beam 天然"看见"3 秒后的状态；本控制器只看当前位置、前瞻点曲率和参考速度。赛车线被挡（对手、障碍、技能效果）时它不会自己绕，需要上面的可选第三层 rollout，那一层要另写，且有成本（约现状的 3%）。
2. **前馈质量决定圈速上限。** 弯道速度由 `PreparePace` 曲线给定。曲线偏乐观则撞墙，偏保守则慢。beam 能部分"自己发现"该减多少速，本控制器把这件事交给离线曲线。曲率必须平滑，2 m 采样噪声会直接传到 ψ_des。
3. **参数依赖更硬。** 开关曲线需要准确的 α（角加速度）与 β（空挡衰减）。prefab 上 `turnInputMultiplier` 出现 1 与 2 两个值，惯量来自日志四舍五入。α 偏差 30% 会表现为过冲或迟钝，症状与现在的摆头相似，容易误判为算法问题。
4. **碰撞后恢复没有被规划。** 撞墙后仍每 tick 给键，通常能收回，但没有"先把车稳住"的判断。这一点不比 beam 差，也不会更好。
5. **难度不再从搜索参数涌现。** Easy/Hard 要显式设计：τ、deadband、反应延迟、目标朝向噪声、专属扭矩 modifier。更可控，但要有人做。
6. **调参期必有抖振。** deadband 太小则键每 tick 左右切换，太大则车头定不住。靠迟滞和离线整圈测试能调好，第一版不会一次到位。
7. **行为更机械。** 五个 AI 同一控制器会开出近乎相同的线。需要各自不同的 `LateralOffset`、τ 和噪声种子，否则观感像火车。

总的权衡：把"驾驭难"从每秒 100 次的在线搜索，换成一次性的离线校准。算力问题消失，校准工作不会消失。

### 风险

- 模型与真实 Rigidbody 在碰撞后的偏差：控制器是闭环的，每 tick 重新读真实状态，对模型误差不敏感，比 3 秒开环 rollout 更稳。
- 赛车线采样 2 m，曲率需要平滑（`PreparePace` 已用 12 m 跨度，沿用）。
- 速度上限的 `ClampMagnitude` 在模型里是硬钳制，引导层在 v ≈ 80 时 a_tangential 应视为 0，不要让它把 ψ_des 拉向切线以外。
- 起步/发车和 handoff 期间 `AIRacerDriver` 已经让出控制权，不受影响。

## 八、"算法偷懒"的边界：哪些可以作弊，哪些不能

用户提出：如果算法难以操控，AI 可以不完全效仿人的操作方式，用 AI 独有的移动方式。意见如下。

**算力上不需要偷懒。** 第六节的控制器每 tick 几十个浮点运算，五个 AI 合起来不到 0.05 ms/帧。现在的算力问题是 beam search 这个具体算法造成的，不是"AI 要像人一样开车"这个目标造成的。换算法之后，算力不再是选择偷懒的理由。

**操控性上可以偷懒，但要走已有的服务器权威路径。** 真正难的不是算力，是这辆车的物理（无阻力、无刹车、车头慢）对任何控制器都苛刻，人类玩家靠练习，AI 靠调参。如果第六节的控制器在真实 Player 上圈速或稳定性仍不满意，按以下顺序放宽，每一级都是 kart 类游戏的常规做法：

1. **AI 专属 stats（最推荐）**。`BuddahPredictedModifierResolver` 已经按对象产出 `FinalTurnTorque`、`FinalForwardForce`、`FinalMaxSpeed`。给 AI 一个专属 modifier：扭矩 ×1.5 让车头响应从 1.3 秒缩到 0.9 秒，控制器立刻好调得多。这不改物理规则、不改碰撞、不改预测路径，玩家感知为"AI 车手更稳"。难度档位也用它：Easy 扭矩 ×1.0、Hard ×1.5。
2. **橡皮筋（rubber-banding）**。按与人类的差距缩放 AI 的 `FinalMaxSpeed`/`FinalForwardForce`（落后 +10%，领先 −10%），同样走 modifier。这是单机竞速保持紧张感的标准手段，成本为零，而且能掩盖控制器在个别弯的失误。
3. **AI 专属速度对齐（谨慎）**。给 AI 加一个小的"速度方向向车头靠拢"的力，相当于只有 AI 有轮胎抓地。它让第六节的引导层退化成普通汽车的 pure pursuit，极易调。代价是 AI 的过弯姿态与人类明显不同（人类必须甩尾，AI 不用），玩家会看出来。只在前两级不够时用，并且也必须走 motor 的力施加路径，不能直接写速度。

**不能做的偷懒**：

- 不要绕过 `BuddahPredictedMotor` 直接写 Transform/Rigidbody 或沿样条插值位置。会破坏碰撞（AI 变成撞不动的墙或穿模）、FishNet 预测与 reconcile、spectator 跟随、`SplineProgressTracker`、技能命中，以及未来联机时的权威一致性。harness.md 明确要求保持服务器权威与预测路由。
- 不要给 AI 单独的物理步长或 tick。

顺序建议：先做第六节控制器，用真实 Player 跑三圈；不满意再上第 1 级；做难度档位时顺手做第 2 级；第 3 级留作最后手段。
